# graphArt_LM

**Teaching a Large language model to read code, and correctly draw the toplogy the code will build; without actually running the code.**

The project will try to build a framework that takes the source code of a model's forward pass and makes a large language model to convert it into a graph : like, the layers / operations are the nodes and the data flowing through them as edges. 

It's pretty obvious once we try to look at a neural network's forward pass routine, as a graph. Actually, PyTorch (for example) can extract this graph automatically by tracing the code; so then you might doubt the point of this project. Usually this graph that is drawn is the running topology that is traced by passing dummy tensors through the network, the differences of this approach against that of LLMs trained for drawing graphs: 
  1. Dynamic vs Static : Notice, for the tracing mechanisms, the networks are actually run to trace out the topology, while the LLMs simply read the code and map out the topology.
  2. Math vs Semantic: The tracing mechanisms actually track the fundamental math - matrix operations and activation functions. But obviously, our LLMs can understand human level semantics and has the capability to convert all those math abstractions to a clean visual graph.
But at the same time, the source code can hide its true structure becuase of loops, conditionals etc. that only show up during run time. We have to test whetere a model can reliable see through this. 


## Two domains, one task

To add some spice to the problem statement, we will also try to teach the LLM on quantum circuit functions too. The core task is still : *code in, topology graph out*. 

> A quantum circuit directed acyclic graph (DAG) is a graph representation where nodes represent quantum gates or operations, and directed edges represent the flow of qubits and sequential dependencies.

## How it works, end to end

```
   source code                 ground truth graph              LLM-generated graph
 (forward() / qnode)   ─┬─►   (auto-extracted via          ┌─►   (from the LLM, given
                         │      torch.fx / circuit_to_dag)  │      only the source code)
                         │                                  │
                         └──────────────► LLM ──────────────┘
                                           │
                                           ▼
                                 compare & score
                          (validity checks + graph metrics)
                                           │
                                           ▼
                              visualize side by side
```

1. **Datset Generation**: Programatically generating a range of classical and quantum architectures, varying in depth, width, and structural pattern

2. **Ground Truth**: For each generated architecture, the computation graphs are extracted using the already present tracing mechanims as discussed above.

3. **LLM Graph Generation**: The model is given only the source code and asked to produce a graph.

4. **Validity, Evaluation, Visualization** :  The generated graph is first checked for structural soundness, then evaluated against the ground truth and compared with rendered graphs. 

> You might point out that the graphs made by the tracing mechanisms from pytorch etc. (eg torch.fx) different from the ones that will be generated by the LLM. The fix is to not compare the raw outputs, but rather design the graph extractors to output the raw graphs to with the same vocabulary as the LLM. Basically, we will try to be mindful of this fact and generate the ground truth graphs in a way that can be compared directly with the LLM generated graphs.

5. **Interface**: An interface for this whole workflow for a user input graph.
 
## Proposed repository structure (LLM generated)

```
graphArt_LM/
├── README.md
├── requirements.txt
├── data/
│   ├── generators/          # scripts that programmatically produce architectures
│   │   ├── classical.py     # PyTorch nn.Module generators
│   │   └── quantum.py       # PennyLane/Qiskit circuit generators
│   └── dataset/             # generated {source_code, ground_truth_graph, metadata} samples
├── graph_schema/
│   └── schema.py            # the shared JSON graph schema (nodes, edges, attributes)
├── ground_truth/
│   ├── classical_extractor.py   # source code -> true graph via torch.fx
│   └── quantum_extractor.py     # source code -> true graph via circuit DAG
├── pipeline/
│   ├── prompts/              # prompt templates for graph generation
│   ├── llm_client.py          # wraps hosted API and local/open model backends
│   └── generate_graph.py      # source code -> LLM-generated graph
├── validation/
│   └── checks.py              # structural validity checks (DAG-ness, connectivity, schema)
├── evaluation/
│   ├── metrics.py             # graph edit distance, node/edge F1, isomorphism, etc.
│   └── run_evaluation.py      # runs the full dataset through the pipeline and scores it
├── visualization/
│   └── render.py               # side-by-side graph rendering, diff highlighting
├── interface/
│   └── app.py                  # interactive demo app
└── reports/                    # write-ups, figures, result tables
```

## Status

This repository is in early setup. The structure above is the target shape of the project; components will be filled in incrementally, starting with the graph schema and the classical ground-truth extractor.
